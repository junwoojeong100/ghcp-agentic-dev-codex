요청서와 지정된 구현·테스트·문서를 함께 대조해, 승인 전 검토용 계획만 작성하겠습니다.

1. 변경 목표와 수정할 파일

변경 전: 120만 원 환불도 요청자가 즉시 완료하며 승인·감사 이력이 없습니다.
변경 후: 서버가 100만 원 이상을 승인 대기로 강제하고, 요청자와 다른 운영 승인자만 승인·반려합니다.
3만 5천 원 등 소액은 즉시 완료 흐름을 유지합니다.

 - src/refunds.mjs: 정책, 상태 전이, 역할 분리, 감사 이벤트, 오류·초기화 구현
 - public/app.mjs: 역할별 버튼·안내, 대기 현황, 감사 타임라인 연결
 - public/index.html, 필요 시 public/styles.css: 승인·반려 입력 및 통제 검증 UI
 - test/refunds.test.mjs: 기존 7개 회귀 테스트를 보존하고 완료 기준 확장
 - README.md: 변경된 업무 흐름, 실행·데모 한계 문서화
 - src/fixtures.mjs 등 제외 파일은 변경하지 않음

2. 완료 기준별 구현 및 검증 방법 (AC-1 through AC-8)

 - AC-1: 서버 기준 1,000,000원 미만 → completed/200, 이상은 pending_approval/202;
policy.enforced=true 경계 테스트.
 - AC-2: process 시 requestedBy 고정. 대기 중 재처리 409이며 금액·요청자 불변 검증.
 - AC-3: 자기 승인·반려 403, 다른 support 403, 다른 approver만 허용해 직무 분리 검증.
 - AC-4: 승인→completed, 반려→rejected. 반려 사유 공백 제외 1~200자와 종결 후 중복 동작 차단 검증.
 - AC-5: 성공·차단 동작마다 순차 ID, 시각, 환불·actor, action/outcome, 금액·사유를 메모리 이벤트에
기록.
 - AC-6: 고액 “승인 요청”, 소액 “환불 처리”, 대기 금액·건수, 승인·반려, 자기 승인 차단 확인, 이름
기반 타임라인을 안전한 텍스트 렌더링으로 제공. actor 변경 시 갱신.
 - AC-7: 알 수 없는 필드·금액 덮어쓰기 400, 미등록 actor 401, 미존재 환불 404, 중복 409 및 응답 복사
검증.
 - AC-8: reset 시 fixture·이벤트·카운터 초기화, 서비스 인스턴스 격리, 기존 7개 테스트 유지 및
경계·전이 테스트 추가.

3. 제외 범위와 위험

실제 결제, 인증, DB, 영구 감사 저장소, 외부 패키지·네트워크·배포는 제외합니다. 역할과 신원은 모의
데이터이며 대기 금액은 절감액이나 예방 성과가 아닙니다. 메모리 이벤트는 서버 재시작 시 사라집니다.

4. 사람의 승인 요청

이 계획은 구현 승인이 아닙니다. 사람이 정책 경계, 역할 분리, 감사 범위와 UI 문구를 검토해 명시적으로
승인한 뒤 다음 역할에 전달해야 합니다. 구현·테스트·검토와 최종 출시 판단은 분리하며 출시는 hold
상태로 유지합니다.
