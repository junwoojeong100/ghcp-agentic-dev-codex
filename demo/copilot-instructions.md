## Workflow

1. Read the source and the request, explain the root cause and propose a concise plan. Wait for explicit plan acceptance before changing files.
2. Implement the approved plan. Use native GitHub Copilot permission prompts for changes and commands that need permission. Never enable unrestricted, assisted, or permanent approval.
3. Run `node --test --test-reporter=tap test/refunds.test.mjs` and `DEMO_APP_ROOT="$PWD" node --test --test-reporter=tap test/acceptance.test.mjs`. The HTTP acceptance test binds only to loopback and does not call a remote service.
4. Fix defects revealed by tests without weakening the immutable acceptance tests. Run `git diff --check` and review the diff before concluding.
5. Clearly separate implemented behavior, executed checks, and remaining production requirements. Production release remains HOLD.

## Clarifications

Only a support actor can start `process`. For an untouched requested refund, an approver actor must receive 403/REQUESTER_REQUIRED and a blocked audit event. Check terminal-state conflicts first so repeated operations remain 409/INVALID_STATE.
Audit reasons must always be meaningful, non-empty strings for successful and blocked actions. An identified actor's attempt to change the amount or submit unknown fields must produce a blocked audit entry with the server's original amount.
The role selector is a demo device, not authentication. Payment, persistent storage and production identity are outside the scope.
Keep the current accessible element IDs and refund-row `data-id` attributes. Label action buttons as `RF-2401 승인 요청`, `RF-2401 승인`, `RF-2401 자기 승인 차단 확인`, and equivalent labels for each refund. Label the rejection input `RF-2403 반려 이유`. Keep HTTP status in the result notice so the presenter can demonstrate the real response.
Respond in concise Korean. The terminal recording and input log are created outside the workspace; do not modify or invent them.
